## 0.2 Кнопка «папка приложения» и сохранность данных при обновлении/переустановке

Запрос: кнопка в тулбаре должна открывать не папку установки, а ту, где лежит
`storage` (`AppData\Roaming\MoonApp`), и обновление/переустановка не должны
трогать `storage` (сейчас «при каждом обновлении удаляются настройки, скачанные
паки и модели»).

**Почему терялось.** До 0.3.4 `storage` лежала рядом с exe, то есть ВНУТРИ
каталога установки. NSIS-инсталлятор перед установкой новой версии тихо запускает
деинсталлятор предыдущей, а тот делает `RMDir /r $INSTDIR`
(`app-builder-lib/templates/nsis/uninstaller.nsh`) — вместе с файлами приложения
удалялась и `storage`: настройки, секреты, модели апскейла, скачанные паки.
Тихое автообновление `electron-updater` докапывает файлы без такой очистки,
поэтому дефект проявлялся при ручной переустановке (0.3.2 → 0.3.3).

**Что сделано — три уровня защиты.**

1. Данные живут в `%APPDATA%\MoonApp\storage` (`app.getPath("userData")`), папка
   установки для данных не используется вообще. Порядок мест:
   userData → `%LOCALAPPDATA%\MoonApp\storage` → папка установки (только крайний
   случай, с явным предупреждением в журнал). `electron/storagePath.js`.
2. NSIS-хук `build/installer.nsh` (подключён как `build.nsis.include`):
   - `customInit` выполняется в `.onInit` ПОСЛЕ чтения `InstallLocation` из
     реестра и ДО `uninstallOldVersion` — старый `storage` переносится в
     `%APPDATA%\MoonApp\storage`: сначала `Rename` (перенос внутри тома
     мгновенный, без копирования гигабайтов моделей), при неудаче — robocopy
     `/E /XC /XN /XO`, то есть копируются ТОЛЬКО отсутствующие файлы, а
     существующие не перетираются;
   - `customRemoveFiles` (деинсталлятор, в т.ч. тихая переустановка) — та же
     страховка перед `RMDir /r $INSTDIR`.
3. `storagePath.js` дополнительно сливает данные из легаси-мест
   (`<install>\storage`, `<install>\storage.legacy`,
   `%LOCALAPPDATA%\MoonApp\storage`) — только недостающее, не перетирая
   имеющееся, — и ставит маркер `.legacy-migrated`, чтобы не обходить дерево
   файлов при каждом старте.

**Кнопка в тулбаре** (`shell:open-app-dir`) открывает родителя `STORAGE_DIR` —
`%APPDATA%\MoonApp` (в dev — корень проекта); подпись обновлена во всех 6 локалях
(«Открыть папку с данными приложения»).

**Как проверено.**

- Поведение хука прогнано настоящим NSIS-компилятором (`makensis`) на
  изолированных каталогах: `A_settings=old-A`, `A_model=yes`, `A_src=moved`
  (перенос целиком, источник освобождён) и `B_settings=old-A`, `B_model=yes`,
  `B_src=kept` (существующие настройки НЕ перетёрты, недостающие файлы
  скопированы).
- `tests/storagePath.test.ts`: слияние без перетирания, отсутствие источника,
  файл на месте каталога — 3 теста зелёные.
- В собранном `app.asar` есть `electron/storagePath.js` с `mergeMissing` и
  маркером `.legacy-migrated`, а `main.js` — с новым обработчиком кнопки.
- `npm run dist` → `check:pack`: ONNX OK, undici OK, каталог моделей на месте.

## 1. Прокси — главная проблема (не работает, хотя показывает «подключено») — ✅ ИСПРАВЛЕНО (см. раздел 0)

### Корневая причина

Индикатор «Подключено» в UI и реальная работоспособность прокси проверяют **разные вещи**.

| Что происходит                                                                                                                                                  | Где в коде                                                                                           |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Готовность ядра sing-box определяется только по открытию **SOCKS-порта**                                                                                        | `server/proxyCore.js:1271-1287`, функция `waitCoreReady()` — вызывает только `isPortOpen(socksPort)` |
| **HTTP-inbound** (порт `httpPort`, объявлен в `buildSingBoxConfig`) вообще не проверяется на готовность                                                         | `server/proxyCore.js:708-723`, `1271-1287`                                                           |
| После проверки только SOCKS-порта выставляется `running: true, enabled: true`                                                                                   | `server/proxyCore.js:1085-1088`                                                                      |
| Индикатор «Подключено» зелёный ровно тогда, когда `core.enabled && core.running`                                                                                | `src/pages/bypass/parts/ProxyPanel.tsx:79`                                                           |
| Но TMDB-клиент (метаданные фильмов, постеры) ходит **не через SOCKS, а через HTTP-inbound** (`undici.ProxyAgent`), потому что undici 6 умеет только HTTP-прокси | `server/middleware/perPageProxy.js:71, 116-131`                                                      |

**Вывод:** если HTTP-inbound не поднялся (конфликт порта, ошибка бинда, гонка при рестарте, блокировка антивирусом второго листенера и т.п.), а SOCKS поднялся — приложение честно показывает «прокси подключён», но все запросы TMDB и картинок фактически идут в обход прокси или не идут вовсе.

### Маскирующий слой: «тихий» fallback на прямое подключение

| Файл / строки                                                        | Проблема                                                                                                                                                        |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server/ts/tmdb.ts:220-241` (`fetchJson`), `:411-434` (`fetchImage`) | Если запрос через прокси падает, код **молча повторяет запрос напрямую** (`attempt(false)`), только пишет `logger.warn("tmdb.proxy_failed_fallback")`           |
| —                                                                    | Поле `via: "proxy"\|"direct"` возвращается из клиента, но не найдено использования в `src/pages/movies` — пользователь не видит, что запрос ушёл в обход прокси |

Итог: ровно симптом из вашего описания — «страница фильмов выбрана через прокси», но по факту либо контент грузится напрямую (и рубится блокировкой без VPN), либо оба пути сломаны, а UI никак не сигнализирует о причине.

### Дополнительные риски

| Проблема                                                                                                                                                                                                                                 | Где                                                                                              |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| TOCTOU-гонка: проверка занятости портов происходит до спавна процесса sing-box, порт может измениться между проверкой и реальным бинд-логом                                                                                              | `server/proxyCore.js:1027-1036`                                                                  |
| Системная склонность к рассинхрону «что проверяем» vs «что реально нужно готово» — уже чинили похожий баг: `pingNode()` раньше искал `sing-box.exe` раньше TCP-проверки узла, из-за чего вместо `unreachable` отдавался `engine_missing` | коммит `3988c6e`                                                                                 |
| Нет теста на сценарий «SOCKS поднялся, HTTP — нет»                                                                                                                                                                                       | `tests/proxyCore*.test.ts`, `tests/proxyPorts.test.ts` — покрытия именно этого случая не нашлось |

### Что чинить (по приоритету)

1. **`waitCoreReady()`** (`server/proxyCore.js:1279`) — дожидаться готовности **обоих** портов (SOCKS и HTTP), а не только SOCKS.
2. Разделить статусы `socksReady` / `httpReady` в `getCoreStatus()` и завязать `ProxyPanel.tsx:79` на то поле, которое реально нужно потребителю (TMDB/LLM — HTTP; yt-dlp — SOCKS), либо показывать оба индикатора отдельно.
3. Убрать «тихий» fallback в `tmdb.ts` или как минимум прокидывать `via: "direct"` на фронт и показывать баннер «TMDB загружен в обход прокси».
4. Добавить кнопку «Проверить прокси сейчас», делающую реальный HTTP GET через оба inbound-порта, а не просто `isPortOpen` — открытый TCP-порт не гарантирует, что TLS/Reality-хендшейк через узел работает.

### Альтернативы TMDB

| Вариант                                                     | Плюсы                                                                                                                                                                 | Минусы                                                                                                               |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Собственное зеркало/кэш-прокси TMDB на своём VPS/домене** | Максимальная совместимость с текущим `tmdb.ts` (тот же формат ответов, почти не нужно менять код нормализации), закрывает и блокировку API, и картинок одним решением | Нужна поддерживаемая инфраструктура (VPS, домен), дополнительные расходы, новая точка отказа на стороне разработчика |

**Рекомендация:** если понадобится страховка от блокировок — собственное зеркало
TMDB (минимум изменений в коде). Попытка использовать Kinopoisk.dev как
альтернативный источник успеха не имела (ключ отклоняется, см. раздел 0) и удалена
из приложения. В первую очередь всё равно нужно закрывать логику проксирования —
иначе никакой источник не заработает надёжно, поскольку ломается сама логика
«помечено как проксируемое, но реально не проксируется».

## 3. Страница «Магазин» (`src/pages/store/StorePage.tsx`)

Это не магазин фильмов, а установщик Windows-приложений (winget + каталог comss.ru + произвольные ссылки). Логика в целом рабочая, но диагностика ошибок слабая.

| Строка                                 | Проблема                                                                                                                                                                                                                          |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `StorePage.tsx:86-90` (`load()`)       | `.catch(() => {})` — ошибка загрузки каталога полностью проглатывается, пользователь видит просто пустой список без объяснения                                                                                                    |

| `StorePage.tsx:208-265` (`parseComss`) | Poll-цикл до 15 минут с фиксированным интервалом 700мс, без exponential backoff — при недоступности comss.ru (тоже блокируемый ресурс) будет тихо крутиться до таймаута                                                           |
| `StorePage.tsx:172-190`, `193-206`     | `install` / `downloadOnly` корректно ловят ошибки и показывают их — тут с UX всё в порядке                                                                                                                                        |

**Вывод:** функционально страница работает (установка, скачивание, избранное, пагинация реализованы), но повторяет тот же паттерн «тихого проглатывания ошибок», что и модуль прокси/TMDB.

## Краткое резюме

**Прокси и каталог фильмов — уже исправлены** (раздел 0): индикатор прокси теперь честно отражает готовность обоих портов sing-box, ключ TMDB вшит намертво в код, а нерабочая альтернатива (Kinopoisk) удалена из приложения. Данные пользователя (`storage`) больше не теряются при обновлении и переустановке (раздел 0.2).

**Главный оставшийся риск** — отсутствие централизованного завершения дочерних процессов (ffmpeg/TTS/diarize/sing-box) при закрытии приложения (раздел 7): при резком выходе во время долгой операции процессы могут остаться висеть в фоне, а частично записанные файлы — повредиться. Это стоит чинить следующим.
