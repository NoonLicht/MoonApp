# MoonApp

Персональная панель утилит для Windows: медиа, обход блокировок, мониторинг железа, книги, ИИ-чат и многое другое — в одном нативном desktop-приложении на Electron.

**Стек:** Electron 31 · React 18 · TypeScript · Vite · Express · SQLite (better-sqlite3) · Vitest

---

## Установка (готовая сборка)

1. Скачайте `MoonApp-Setup-x.y.z.exe` со страницы [Releases](https://github.com/NoonLicht/MoonApp/releases).
2. Запустите установщик. По умолчанию приложение ставится в `%LOCALAPPDATA%\Programs\MoonApp` (права администратора не нужны, путь можно изменить).
3. Рядом с программой создаётся папка `storage\` — в ней хранятся все данные.

> **Примечание:** Windows SmartScreen может предупредить о неизвестном издателе — сборка пока не подписана сертификатом. Нажмите «Подробнее» → «Выполнить в любом случае».

Чтобы инсталлятор оставался разумного размера, часть инструментов скачивается автоматически при первом использовании соответствующей функции (все — в `storage\`), а `yt-dlp` и `sing-box` теперь поставляются **в комплекте** с инсталлятором:

| -------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| FFmpeg (+ ffprobe)                                 | `storage\ffmpeg\`                                                                              | скачивается при первом использовании (конвертация / сжатие видео / TTS)                                                              |
| yt-dlp                                             | в комплекте (`resources\app.asar.unpacked\server\vendor\ytdlp`), фолбэк — `storage\ytdlp\`     | страницы «Видео» и «Музыка» — из коробки                                                                                             |
| sing-box                                           | в комплекте (`resources\app.asar.unpacked\server\vendor\singbox`), фолбэк — `storage\singbox\` | страница «Прокси» — из коробки                                                                                                       |
| Zapret-движок                                      | `storage\zapret\`                                                                              | скачивается на странице «Обход блокировок»                                                                                           |
| whisper.cpp + модель `ggml-small`                  | `storage\whisper\`                                                                             | скачивается скриптом `npm run fetch:whisper` **или прямо в приложении** (страница «Лекторий» → кнопка-иконка ⚙ «Модель и ускорение») |
| Диаризация sherpa-onnx (бинарь + 2 модели, ~54 МБ) | `storage\diarize\`                                                                             | скачивается кнопкой-иконкой 👥 на странице «Лекторий» → панель **«Говорящие»**; нужен Windows 10+ (распаковка через `tar.exe`)       |
| LibreHardwareMonitor                               | в комплекте (`resources\app.asar.unpacked\server\vendor\lhm`)                                  | монитор системы — из коробки                                                                                                         |

> При сборке инсталлятора бинарники yt-dlp/sing-box подкладываются скриптом
> `npm run fetch:engines` (см. `scripts/fetch-engines.js`); в репозиторий `.exe` не коммитятся.
> Движок распознавания лекций качается отдельно (`npm run fetch:whisper`) — модель
> весит ~466 МБ, поэтому в инсталлятор не входит.
>
> Модель и сборку движка можно выбрать в самом приложении: страница «Лекторий» →
> кнопка-иконка **⚙ «Модель и ускорение»** в правом верхнем углу (подписи у кнопок
> страницы убраны — название показывается подсказкой
> при наведении; в Настройках эти панели не дублируются). Там
> скачиваются модели tiny … large-v3 (+ q5-кванты) и сборки движка — CPU,
> OpenBLAS и CUDA 11.8/12.4: CUDA включает счёт на видеокарте NVIDIA, а кнопка
> «Проверить движок» прогоняет тестовый WAV и показывает реальный бэкенд.
>
> **AI-конспект** (страница «Лекторий» → кнопка «ИИ-конспект»): провайдера и
> модель можно выбрать явно (по умолчанию **DeepSeek**), режим запуска —
> «умный авто» (сам после записи, но только если текста достаточно и он вырос с
> прошлой сборки), «всегда авто» или «вручную».
>
> **Разделение говорящих** (кнопка «Говорящие»): системный звук и микрофон пишутся
> в две дорожки, поэтому лектор и аудитория разделены уже «из коробки». Для
> различения голосов ВНУТРИ дорожки (кто из студентов отвечал) нужен пакет
> sherpa-onnx (~54 МБ, скачивается кнопкой). Разбор идёт на процессоре
> (~1 минута аудио за 5 секунд), поэтому авто-режим по умолчанию **выключен**.

## Запуск из исходников

Требуется **Node.js ≥ 20** (разрабатывался на 22/24).

```bash
git clone https://github.com/NoonLicht/MoonApp.git
cd MoonApp
npm install

# сборка нативного модуля better-sqlite3 под Electron
npm run rebuild:electron

# запуск в dev-режиме (Vite + Electron + сервер)
npm start
```

В dev-режиме данные хранятся в `storage/` рядом с проектом (путь можно переопределить переменной окружения `MOONAPP_STORAGE`).

## Апскейл медиа: живой каталог моделей, плавность, проба

Модели качаются по требованию в `storage\models\upscale\` — кнопкой в приложении
(страница «Апскейл» → **Модели**: категории, размер, лицензия, прогресс загрузки,
«Оптимальные настройки», «Удалить») или скриптом `npm run fetch:models`.

**Каталог — «живой»: его не нужно ждать вместе с обновлением приложения.**
Список моделей лежит в репозитории (`server/models.manifest.json`, ветка `master`) и
забирается кнопкой **«Обновить каталог»** в панели «Модели ONNX». Источники по приоритету:

1. `storage\models\models.manifest.json` — скачанный каталог (его создаёт кнопка). Он
   перекрывает вшитый целиком: добавили модель в репозитории — она появилась у
   пользователя, убрали — исчезла из списка (сам `.onnx` с диска не удаляется);
2. `server/models.manifest.json` — вшитый в сборку (первый запуск, офлайн).

Скачивание идёт с `raw.githubusercontent.com` и, если он недоступен, с зеркала
`cdn.jsdelivr.net`. **Свой адрес каталога** (например, отдельный репозиторий только с
манифестом) задаётся переменной окружения:

```bash
MOONAPP_MANIFEST_URL=https://raw.githubusercontent.com/you/catalog/main/models.manifest.json
```

Скачивание безопасно для уже работающего каталога: записи проверяются (id, имя файла без
разделителей пути, ссылка только `http(s)`, `sha256` из 64 hex), мусор отбрасывается,
файл пишется через `.tmp` + rename. Ошибка (нет сети, 404, битый JSON, пустой список)
оставляет прежний каталог и показывает понятный текст в панели — есть коды для всех
локалей. После обновления панель пишет, откуда список и когда он обновлён
(«Каталог из GitHub · 27 моделей · обновлён 20.09.2026, 14:12»).

В каталоге у каждой модели есть `tags` (категории для фильтра) и `rec` — оптимальные
настройки именно для неё (множитель, тайл, перекрытие, шум, резкость), их подставляет
кнопка «Оптимальные настройки». Своя модель добавляется записью в манифест:

```json
{
  "id": "my-model",
  "label": "My Model x4",
  "file": "my-model.onnx",
  "kind": "upscale",
  "scale": 4,
  "sizeMb": 64,
  "license": "MIT",
  "url": "https://example.com/my-model.onnx",
  "sha256": "0123…",
  "tags": ["photo"],
  "rec": { "scale": 2, "tile": 256, "overlap": 16, "sharpen": 0, "denoise": 0 },
  "_hint": "Чем эта модель хороша"
}
```

- `url: ""` — кнопки «Скачать» у модели нет; `sha256` (если задан) сверяется при загрузке;
- `kind: "interp"` — интерполятор кадров, тогда нужны `mult` и `inputSig`;
- `batch: 1` — граф принимает ровно один вход за проход (пачка невозможна; см. ниже),
  `batch: N>1` — предел динамической оси, поля нет — неизвестно (движок проверит сам);
- `align: N` — граф принимает только кратные N стороны (Real-CUGAN: внутри UNet1 есть
  down/up-семплинг). Движок добирает тайл повтором крайней строки/столбца и обрезает
  результат при вклейке, поэтому пользовательский тайл и последний тайл кадра любого
  размера работают как есть;
- `provider: "cpu"` — рекомендация автора модели: граф не работает на GPU. Пример —
  Anime4K: DirectML роняет его Add (`0x8007023E`), поэтому движок ставит CPU первым
  в списке попыток (явный выбор провайдера в настройках это не отменяет);
- файл, скопированный в `storage\models\upscale\` вручную под именем из `file`,
  показывается как установленный сразу.

## Апскейл: модели из официальных весов (Real-CUGAN, Real-ESRGAN Compact, Anime4K)

Часть каталога собрана нами из официальных весов, потому что готовых ONNX в открытом
доступе нет (у Real-CUGAN и IFRNet лежат только `*.pth`). Инструменты:

```bash
# Real-CUGAN 2x из официальных весов bilibili/ailab (MIT)
python scripts/export-upscale-onnx.py --model cugan --scale 2 \
  --weights up2x-latest-denoise3x.pth --src ailab/Real-CUGAN --out cugan-2x-denoise3x.onnx
# Real-ESRGAN Compact (realesr-animevideov3, BSD-3-Clause)
python scripts/export-upscale-onnx.py --model esrgan-compact \
  --weights realesr-animevideov3.pth --out realesr-compact-x4.onnx
# fp16-граф → fp32-интерфейс: ONNX Runtime не принимает fp16-входы из JS
python scripts/export-upscale-onnx.py --model fp32-wrap \
  --weights Anime4K_Upscale_GAN_x3_L.onnx --out anime4k-x3-l-fp32.onnx
```

Что собрано (всё проверено реальным инференсом — `npm run verify:model -- <ид>`):

| Модель                | Множитель | Источник весов                               | Особенность                                                         |
| --------------------- | --------- | -------------------------------------------- | ------------------------------------------------------------------- |
| `real-cugan-2x-anime` | ×2        | Real-CUGAN `-denoise3x`                      | лучшая чистка шума и артефактов сжатия на аниме, `align: 4`         |
| `real-cugan-3x`       | ×3        | Real-CUGAN `-conservative`                   | компромисс «время/детализация» для 720p                             |
| `real-cugan-4x`       | ×4        | Real-CUGAN `-conservative`                   | детализация для 480p/720p аниме и старых фото                       |
| `realesr-compact-x4`  | ×4        | Real-ESRGAN Compact (`realesr-animevideov3`) | 2.4 МБ, ~75 мс на 64×64 — дешёвая покадровая обработка видео        |
| `anime4k-x3-l`        | ×3        | Anime4K (gradation L)                        | fp16 пересобран в fp32-интерфейс, работает на CPU (`provider: cpu`) |

Файлы лежат в `NoonLicht/MoonApp-Upscale-ONNX` (граф + веса, README с лицензиями),
ссылки и `sha256` — в каталоге. Пресеты: «Аниме-видео: чистка (×2)», «Аниме-видео:
Anime4K (×3)», «Видео: компактная модель», «Аниме-арт: Real-CUGAN ×4»; всего в
каталоге **30 моделей** (апскейлеры + интерполяторы) и **21 системный пресет**.

`npm run verify:model -- <ид> --update-manifest` не только сверяет `sha256` и меряет
скорость, но и **сам определяет факты графа**: множитель (по выходу на 64×64),
порядок каналов (RGB/BGR), поддержку пачки и **кратность сторон** — для этого
проверяются размеры 64, 66 и 65: если 66 проходит, а 65 нет — нужны чётные
(`align: 2`), если и 66 падает — кратные четырём (`align: 4`). Найденная кратность
попадает в каталог, а уже записанная бо́льшая не понижается (движок замеряет на CPU,
на DirectML требование может быть жёстче).

## Апскейл: точность (ONNX/FP16) и TensorRT

Точность ONNX-модели — это точность её файла: обычно FP32, fp16-экспорты движок
подхватывает сам (конвертирует тензоры на границе ORT по метаданным графа). Для
владельцев NVIDIA есть второй путь — **TensorRT**: панель «Модели ONNX» показывает
строку готовности и кнопку **«Собрать движок TensorRT FP16»** у скачанной модели.

- сборка компилирует граф под вашу GPU (профиль формы берётся из тайла модели) и кладёт
  `.engine` в `storage\models\upscale\.trt` — дальше он грузится из кэша;
- в Pro-настройках появляется провайдер **TensorRT (FP16)** и строка «Точность»:
  `как в модели (FP32)` для обычного пути или `TensorRT FP16 (видеокарта NVIDIA)`;
- для AMD/Intel/CPU ничего собирать не нужно: работает обычный ONNX-путь (DML/CPU);
- кнопка появляется только там, где провайдер реально есть в сборке ONNX Runtime
  (`listSupportedBackends`): иначе панель честно пишет, что это не про ONNX-путь;
- FP8/INT8 не поддерживаются: им нужна отдельная калибровка (в каталоге таких файлов нет).

Ссылка может вести и на **zip-архив** — так раздают модели Qualcomm (AI Hub): внутри
`.onnx` плюс отдельный файл весов (`*.data`). Загрузчик распаковывает архив сам: граф
ложится под именем из каталога, веса и метаданные — рядом с ним (ONNX Runtime ищет их по
той же папке), а список файлов запоминается, чтобы кнопка «Удалить» убрала модель
целиком, а не только граф. `sha256` для таких моделей — хеш самого архива.

Правку манифеста в рабочей копии видно без перезапуска сервера (кэш — по времени правки
файла), а для пользователей достаточно запушить манифест и нажать «Обновить каталог».
Честные факты (`sha256`, настоящий множитель, порядок каналов RGB/BGR, время) удобнее не
писать руками, а получить командой
`node scripts/verify-model.js --url <URL> --id <ид> --update-manifest` — она сама допишет
`sizeMb`, `sha256`, `scale`, `bgr` и `_measured`. Скрипты (`fetch-models.js`,
`verify-model.js`) читают тот же каталог: скачанный из приложения важнее вшитого
(`scripts/manifest.js`).

Всё, что в каталоге помечено измеренным (`_measured`), проверено живым скачиванием и
прогоном через `onnxruntime-node` (форма входа/выхода, настоящий множитель, порядок
каналов, время) — `sha256` из манифеста сверяется при каждой загрузке.

Модели живут в памяти только во время работы: как только последнее задание очереди
закончилось, движок вызывает `release()` у сессий и отдаёт память устройства (раньше
кэш просто очищался, а ONNX-сессии оставались загруженными до выхода из приложения —
видеопамять при этом выглядела «занятой навсегда»). Если задание ещё считает,
выгрузка откладывается до его окончания: `release()` во время инференса ломает сессию.
Очередь из нескольких файлов модель не пересоздаёт — выгрузка происходит после
последнего задания.

**Размер пачки кадров: значение по умолчанию — «Авто».** ONNX-инференс быстрее, когда
кадры считаются заходом (одна раскладка `[n,3,h,w]` на тайл вместо n вызовов), но пачка
держит в памяти буферы кадров, поэтому её размер считается от **фактически свободной
памяти**, а не от фиксированного бюджета: RAM — 40 % свободной памяти машины (не больше
6 ГБ), VRAM — свободная видеопамять минус модель и резерв. Раньше в этой формуле стояли
жёсткие 1.5 ГБ, из-за которых запрос 32/64 на 1080p×4 молча превращался в 14–16 кадров
даже при 17 ГБ свободной памяти. Ручные значения (1…128) уважаются ровно настолько,
насколько хватает памяти, «Авто» берёт максимум (потолок 64) — пачка целиком идёт одним
заходом, а не режется на «порции»: за отзывчивость «Стопа» отвечают проверки флага между
тайлами прямо в функциях инференса. Нет данных о видеокарте (CPU или встроенная графика) —
считаем только по памяти кадров; видеопамяти не хватает даже под модель — работаем по
одному кадру.

**Пачку принимает не каждая модель — это видно и в списке, и в каталоге.** Поле `batch` в
манифесте означает, сколько кадров граф принимает за один `session.run`: `1` — жёстко один
(так у большинства Real-ESRGAN: ONNX отвечает «index: 0 Got: 64 Expected: 1»), нет поля —
неизвестно. Для моделей с `batch: 1` настройка пачки **не показывается вовсе** (в её месте
подпись «По одному кадру за проход»), а движок не копит очередь: раньше запрос пачки 64
заставлял пайплайн ждать 64 кадра, обрабатывать их по одному, потом снова ждать — в
мониторе это «лестница» с периодом в размер пачки и постоянные паузы видеокарты, плюс
сотни мегабайт под полные кадры результата. Факт про пачку определяется автоматически
(`node scripts/verify-model.js <ид>`: проба из двух кадров и двух тайлов, при отказе в
манифест пишется `batch: 1`), а если модель ещё не проверена, движок пробует пачку сам,
ловит отказ и запоминает его — с той же ошибкой в логе (`upscale.batch_fallback` /
`upscale.batch_single`).

**Второй размер пачки — у интерполятора.** Поле «Пакет тайлов интерполятора» задаёт, сколько
тайлов пары считается одним заходом (0 — «Авто»: до 4 тайлов); у наших экспортов IFRNet/CAIN/
RIFE в ONNX размечена динамической только ось h/w, поэтому для них (как и для апскейлеров
с `batch: 1`) настройка скрыта, а тайлы считаются по одному. В один заход складываются
только тайлы одного размера — края кадра меньше, и смешивать их с полными нельзя.

**Очередь работает с опережением на одну пачку** (двойная буферизация, `QUEUE_BATCHES = 2`):
пока GPU считает текущую пачку, декодер успевает набрать следующую, а бюджеты памяти уже
учитывают это удвоение. До этого чтение из `ffmpeg` ставилось на паузу на всё время
инференса, поэтому видеокарта простаивала между «залпами»; кадры «в работе» учитываются и
при закрытии входа энкодера, иначе последняя пачка падала бы с «write after end».

**Можно считать только плавность, без апскейла** (в списке моделей — «Без апскейла (только
плавность)»). Тогда ONNX-апскейлер не запускается вовсе: кадры идут в энкодер как есть,
работают интерполяция, замедление и перекодирование, а размер кадра остаётся исходным
(множитель разрешения не применяется). Это нужно, когда разрешение уже достаточное, а
поднять надо только частоту кадров — и заодно экономит самый дорогой этап. Для фото этот
режим превращается в обычное перекодирование (со сменой формата/масштабом ffmpeg).

**Множитель плавности ограничен возможностями модели, а не общим потолком.** Схема с
моментом времени (RIFE, IFRNet) считает любой кадр между парой, поэтому ×2/×3/×4 работают
напрямую, без каскадов: ×3 — это две вставки с `t = 1/3` и `2/3` на каждый переход. CAIN
интерполирует ровно середину пары и момент времени не принимает — для неё движок оставляет
только ×2 (иначе получились бы два одинаковых «средних» кадра, формально верное число
кадров и испорченная картинка); сервер урезает запрос и пишет об этом в журнал, а UI просто
не предлагает лишние пункты (`multMax` в каталоге моделей).

**Порядок интерполяции выбирается в Pro-настройках** («Где интерполировать»), и это
общая настройка для обоих режимов плавности:

- **до апскейла** — вставки считает интерполятор по исходным кадрам (дешевле: меньше
  пикселей), а апскейлер получает уже в 2–4 раза больше кадров (дороже ровно на этот
  множитель). У ffmpeg-режима это фильтр `minterpolate` в декодере, у ONNX-модели —
  вставки между исходными кадрами перед отправкой их в апскейл;
- **после апскейла** — наоборот: апскейлер работает по исходному числу кадров, а
  интерполятор — по увеличенным (на 4K дорого, поэтому для ONNX-моделей RIFE/CAIN это
  по умолчанию в пресете «Плавность моделью»).

Порядок выходного потока в обоих случаях один и тот же (`up₀ → ins → up₁ → …`), поэтому
звук и субтитры остаются синхронными: вставок всегда `mult − 1` между кадрами и ни одной
после последнего. В режиме ONNX-модели частота результата всегда выходная (`-r` входного
rawvideo — `outRate`), иначе ffmpeg растянул бы видео в `mult` раз, а `-shortest` обрезал
его по звуковой дорожке — проверено прогоном 40 кадров ×2: оба порядка дают 79 кадров
@ 50 fps и 1.58 с (у исходника 25 fps и 1.6 с).

**«Стоп» — это стоп-кран, а не «мягкая просьба».** ONNX-заход прервать нельзя, поэтому флаг
остановки проверяется между тайлами прямо в функциях инференса (`upscaleRgb`,
`upscaleRgbBatch`, `interpolatePair`), а остановка — ещё и перед каждым готовым кадром (там
считается интерполяция). Задание, которое ещё стоит в очереди, отменяется сразу, не дожидаясь
старта.

Сверх этого ffmpeg-процессы задания (декодер и энкодер) регистрируются в движке и гасятся
прямо из `cancelJob` (`upscale.procs_killed`), не дожидаясь, пока конвейер дойдёт до проверки
флага, а ONNX-сессии после остановки выгружаются немедленно — даже если в очереди остались
другие файлы (`upscale.session_released` для каждой модели). Замер на реальном задании
(640×360, апскейл ×2 + RIFE ×2, модели через DirectML): задание остановлено через **246 мс**,
ffmpeg погашен через **300 мс**, видеопамять вернулась к базовой (**2215 → 1550 МБ**) уже
**через секунду** после нажатия «Стоп». ONNX Runtime в консоли теперь молчит до ошибок
(`logSeverityLevel: 3`) — его предупреждение про ноды, уведённые на CPU, было штатным, но
выглядело как сбой.

### Форум-трекер и Cloudflare

Поиск раздач работает во вкладке «Поиск раздач» плеера (страница «Фильмы»):

1. один раз укажите логин и пароль форума — они сохраняются в зашифрованных секретах
   (`storage/secrets.json`), а сессия форума (куки) — в `storage/trackers/`;
2. вкладка открывается с уже подставленным названием фильма и сразу ищет по нему;
3. раздачу открывает бэкенд: он скачивает `.torrent` своими куками и отдаёт плееру список серий.

Если форум отвечает страницей проверки **Cloudflare** («Just a moment…», HTTP 403) — значит,
запросы идут с IP, которому Cloudflare не доверяет. Решение — **вход в окне приложения**:

1. включите прокси для страницы «Фильмы» (панель прокси → «страница → прокси») — окно входа
   возьмёт тот же прокси, поэтому cf_clearance будет выдан тому же IP, что и у поиска;
2. в плеере: вкладка «Поиск раздач» → «Войти на форум» — откроется окно Chromium приложения
   на странице входа. Войдите (и пройдите проверку Cloudflare, если она появится) — окно
   закроется само, куки подхватятся автоматически;
3. дальше поиск раздач и скачивание `.torrent` идут через сессию Chromium приложения
   (сетевой стек браузера), поэтому форум видит обычный браузер.

Порядок работы окна (важно для rutracker):

- окно **не закрывается само**, пока в куках нет `bb_data` — куки `bb_guid`, `bb_ssl`,
  `bb_session` форум ставит и гостю, поэтому по ним окно раньше закрывалось сразу после
  проверки Cloudflare, и пользователь не успевал войти (это и была причина «поиск не
  работает после входа»);
- заголовок окна подсказывает этап: «Пройдите проверку Cloudflare» → «Проверка пройдена,
  войдите (логин/пароль)»;
- когда вход выполнен, окно закрывается само, куки и User-Agent переносятся в сессию
  поиска. Если проверка пройдена, а вход не выполнен, приложение входит логином и
  паролем из настроек само (POST `login.php` идёт тем же стеком Chromium).

Три детали, без которых окно входа не работает (проверено на живом rutracker):

- **User-Agent.** У Chromium приложения по умолчанию UA содержит имя приложения и `Electron/…` —
  Cloudflare считает такой отпечаток ботом и отдаёт проверку даже настоящему браузеру. Сессии окна
  входа ставится обычный Chrome-UA той же версии Chromium (`electron/main.js` → `trackerChromeUa`),
  и тот же UA уходит в заголовках поиска: `cf_clearance` привязан к паре **IP + User-Agent**;
- **Путь куки.** rutracker выставляет куки сессии (`bb_data` и др.) с `Path=/forum/`, поэтому куки
  читаются без фильтра по URL и фильтруются по домену (`trackerCookies` в `main.js`,
  `syncChromiumCookies` в `server/ts/trackerScraper.ts`) — иначе вход выглядел бы невыполненным;
- **Нет куки — нет входа.** Если после закрытия окна куки не появились, UI сообщает об этом прямо
  (код `no_cookies`), а не показывает «куки сохранены»: значит проверку Cloudflare пройти не удалось.

Важно про неизменность пары «IP + User-Agent»: `cf_clearance` выдаётся на конкретный IP и UA, и
если потом сменить прокси (или UA), форум снова отдаст проверку — тогда помогает кнопка
«Пройти проверку Cloudflare заново» (то же окно). По этой же причине поиск всегда идёт тем же
транспортом, что и окно: сетевой стек Chromium приложения (`session.fetch`), а не обычный запрос
сервера. В диагностике ошибки `cf_challenge` теперь видно всё сразу — `transport`, `userAgent`,
`proxy`, список куки и признак входа `hasLogin`.

Поиск в браузерном режиме (интерфейс открыт в браузере, не в приложении) проверку Cloudflare не
проходит — там нет Chromium-сессии; UI прямо предупреждает об этом и предлагает запустить приложение.

Скрапер получает сессию окна входа через `bindChromiumSession` (вызывает `electron/main.js`),
а вне Electron работает обычным `fetch` с per-page прокси — вкладка «Поиск раздач» открывается и
в браузере, но проверку Cloudflare такой запрос не проходит (нет Chromium-сессии): в браузере
доступна только ручная вставка куки, и UI говорит об этом.

Почему нельзя просто «взять куки из вашего браузера»: начиная с Chrome/Edge 127 куки шифруются
app-bound-ключом (`v20`), который доступен только самому браузеру — прочитать их извне нельзя,
и Chrome/Edge держат базу куки открытой без разрешения на чтение (любое копирование падает с
`EBUSY`). В списке «Что проверено» это видно как «app-bound» / «база занята». Кнопка
«Подхватить из браузера» осталась для Firefox и Chromium-версий без app-bound (там работает
DPAPI + AES-GCM; ключ из `Local State` читается как base64 от «DPAPI» + blob), а «Вставить
вручную» — запасной путь: F12 → Network → запрос к форуму → Request Headers → Cookie
(через `document.cookie` не выйдет: куки помечены HttpOnly).

Приложение не решает капчу и не подстраивает браузерные проверки «наугад»: при неудаче в ответе
API возвращается код `cf_challenge` с диагностикой (статус, размер, начало ответа форума,
транспорт, UA, прокси, куки) — она видна в интерфейсе и в логах.

### Другой трекер: RuTor (rutor.info)

Поиск раздач можно вести на двух площадках — в плеере есть переключатель **«Трекер»**
(вкладка «Поиск раздач»). **По умолчанию выбран RuTor**: он отвечает без Cloudflare, и вход для
поиска ему не нужен. Если rutracker.org (или сама площадка RuTor) отдаёт проверку Cloudflare, а
пройти её с текущего маршрута не получается — так бывает и в обычном браузере, когда IP не нравится
Cloudflare, — переключите трекер:

- **RuTracker** (`rutracker.org`) — phpBB-форум: cp1251, POST-поиск по `nm`, вход обязателен,
  `tracker.php` закрыт Cloudflare Bot Management;
- **RuTor** (`rutor.info`) — utf-8, запрос уходит **частью пути** (`/search/0/0/000/0/<запрос>`),
  **вход не нужен**: и поиск, и `.torrent` доступны анонимно, поэтому для него скрыты блоки
  логина/куки, а статус сразу показывает готовность к поиску.

Переключение применяет пресет площадки **целиком** (`server/ts/trackerProviders.ts` →
`POST /movies/tracker/preset`): адрес, пути, кодировка, способ поиска и движок разбора выдачи.
Логин/пароль не затрагиваются: они в зашифрованных секретах, а сессии разных трекеров не
пересекаются (файл сессии называется по хосту, `storage/trackers/session-<host>.json`).
Выбор хранится в `settings.json` (`trackers.engine`). У настроек, сохранённых до появления этого
поля, движок определяется по адресу площадки при загрузке (разовая миграция в `server/ts/settings.ts`),
поэтому старый конфиг rutracker не начнёт разбираться движком RuTor. Свой трекер добавляется в
`server/ts/trackerProviders.ts` (пресет) + `server/ts/trackerParse.ts` (разбор выдачи, чистые
функции с тестами); сеть, сессия и кэш — в `server/ts/trackerScraper.ts`.

### Плеер и загрузки (вкладка «Скачанные»)

Плеер у торрента — **свой** (`src/pages/movies/parts/VideoPlayer.tsx`), а не нативные `controls`:
панель стилизована под тему и содержит перемотку со шкалой буфера, play/pause, ±10 секунд,
громкость и Mute, скорость, выбор аудиодорожки, субтитры, **вписывание кадра** (вписать целиком,
заполнить с обрезкой, по ширине, по высоте) и **зум 100–400 % с панорамированием**
перетаскиванием мыши, «картинка в картинке» и полный экран. Пропорции кадра не искажаются:
режимов «растянуть» и «умное растяжение» в панели нет. Горячие клавиши: `Space`/`K` — пауза,
`←`/`→` — ±10 с, `J`/`L` — ±30 с, `M` — звук, `F` — полный экран.

**Смотреть можно во время скачивания.** Поток отдаётся по HTTP Range, поэтому WebTorrent докачивает
именно те куски, которые нужны проигрывателю (`server/routes/movies.js` → `/torrent/stream/…`),
а выбранный файл раздачи получает последовательную стратегию (`torrent.strategy = "sequential"`) —
куски приходят по порядку, а не «где повезло». Прогресс и скорость видны в плашке на видео.

**Как файл попадает в плеер (это важно для MKV).** Раздачи почти всегда в MKV, а Matroska браузерный
движок (Chromium) не демуксит вообще, плюс в раздачах часто звук AC3/DTS, который он тоже не читает.
Поэтому перед воспроизведением приложение решает, каким способом отдавать файл
(`server/ts/mediaProbe.ts` → `playbackPlan`, режим — в ответе `/torrent/tracks` как `plan`):

- `direct` — mp4/webm с h264/vp9/av1 и aac/opus/mp3: файл играется как есть, с нативным seek;
- `remux` — чужой контейнер (MKV/AVI) или неподдерживаемый звук: видео **копируется** без потерь,
  звук перекодируется в AAC, поток отдаётся fragmented MP4 (`/torrent/remux/…?video=copy`);
- `transcode` — кодек, которого Chromium не читает (HEVC, MPEG-2, VC-1): видео перекодируется
  на лету (`video=h264`), поэтому старт занимает несколько секунд;
- `unsupported` — FFmpeg не найден: играть нечего, и плеер говорит об этом прямо, а не «сбой потока».

**Энкодер для перекодирования выбирается по сборке FFmpeg.** Раньше аргументы жёстко
просили `-c:v libx264`, а в сборке с gyan.dev («essentials») он **отключён**
(`--disable-libx264`) — шаг `transcode` падал мгновенно с «Unknown encoder 'libx264'»
(видно в `storage/logs/audit.log`), то есть последняя ступень лестницы не работала вовсе,
а раздачи с HEVC не играли совсем. Теперь `pickH264Encoder` (server/ts/mediaProbe.ts)
берёт первый рабочий из приоритета `libx264 → libopenh264 → h264_mf → h264_nvenc →
h264_qsv → h264_amf` (аппаратные — в конце: их наличие в `-encoders` не значит, что они
запустятся без нужного GPU и драйвера), и под каждый энкодер подставляются СВОИ опции
скорости (`h264EncoderArgs`): `-preset ultrafast -crf` понимает только libx264, у
`libopenh264` — `-b:v`, у `h264_mf` — `-rate_control`, у NVENC/QSV/AMF — свои ключи.
Если в сборке нет ни одного H.264-энкодера, роут честно отвечает
`ffmpeg_encoder_missing` (501), а не сыпет «сбой потока».

Если поток всё-таки не открылся, плеер **сам спускается на ступень ниже** (direct → remux → transcode),
а кнопка **«Пересоздать поток»** на месте ошибки перезапрашивает поток с текущей секунды.

**Шкала и перемотка.** Длину фильма плеер берёт из ffprobe (`durationSec`), а не из
`<video>`: живой поток ffmpeg (fragmented MP4) не содержит длительности, браузер отдаёт
`Infinity`, и раньше шкала схлопывалась в пару секунд — из-за этого ползунок «прыгал» и
перемотка уводила фильм в начало. Теперь:

- шкала всегда идёт на всю длину фильма (`2:32:13`, а не «15 секунд»);
- поверх неё светлая полоса показывает, **докуда можно перематывать** — это доля
  скачанного файла раздачи (последовательная стратегия качает куски по порядку);
- перемотку за пределы скачанного плеер не выполняет молча: он встаёт на границу и
  пишет «Скачано до …», а не начинает фильм заново;
- поток ffmpeg пересоздаётся **на отпускании ползунка**, а не на каждое его движение
  (иначе на один драг уходили десятки запросов с новым ffmpeg);
- после перемотки позиция сохраняется: и ручное «Пересоздать поток», и автоспуск на
  remux/transcode продолжают с той же секунды.

Сам `-ss` по потоку раздачи точен: ffmpeg попадает в ту же позицию, что и при чтении
файла с диска (проверено сравнением кадров 1:1), поэтому «секунда из шкалы» и «кадр на
экране» совпадают.

**Синхрон звука и картинки после перемотки.** Это отдельная и самая коварная поломка:
при `-c:v copy` ffmpeg начинает видео с **ключевого кадра строго ДО** секунды реза
(`-ss`), а звук обрезает ровно по ней — картинка уходит вперёд звука на длину GOP. Это
не «поправить флагами», а свойство копирования: две точки не совпадают никогда.
Живой замер на раздаче H.264 + AC3 (GOP 2.294 с), чтение нашего же Range-стрима, рек на
секунде `1181.138` — она же ключевой кадр:

| команда                                                                           | первый кадр видео                    | точка звука    | расхождение            |
| --------------------------------------------------------------------------------- | ------------------------------------ | -------------- | ---------------------- |
| `-ss 1181.138 -c:v copy` (как было)                                               | `1178.844`                           | `1181.138`     | **2.294 с**            |
| то же + `-avoid_negative_ts make_zero` / `-noaccurate_seek` / `-seek_timestamp 1` | `1178.844`                           | `1181.138`     | 2.294 с                |
| `-ss 1181.138 + 0.15…0.25 -c:v copy`                                              | `1181.138`                           | `1181.288…`    | 0.15 с (знак меняется) |
| input-seek + output-seek, `copy`                                                  | поток битый: первый кадр не ключевой | —              | —                      |
| **`-ss 1181.138` + перекодирование**                                              | **`1181.138`**                       | **`1181.138`** | **0**                  |

Отсюда правило, которое теперь зашито в коде: **старт с нуля копируется, перемотка —
перекодируется**. Что сделано:

- **`exactSeekVideoMode` (`server/ts/mediaProbe.ts`)**: в роуте `/torrent/remux` при
  `start>0` видео принудительно уходит на `-c:v h264`, даже если клиент попросил `copy`.
  Точный seek (`accurate seek`) отбрасывает кадры до запрошенной секунды, поэтому и
  картинка, и звук стартуют ровно в ней. Проверено тем же сравнением кадров: SSIM
  первого кадра потока максимален на `1181.5` (0.947), а не на ключевом кадре `1181.138`
  (0.854) — то есть поток начинается там, где просил плеер;
- **`exactSeekLevel` (`src/pages/movies/lib/playback.ts`)**: любая перемотка (`atSec > 0`)
  ставит ступень, на которой видео НЕ копируется, — это касается ползунка, кнопки
  «Пересоздать поток», смены аудиодорожки, автопродолжения с сохранённой секунды и
  автоспуска после сбоя потока;
- **честная секунда старта (вариант «3»)**: плеер спрашивает её у бэкенда
  (`/torrent/seek?copy=0`) и получает `{ requested, startSec, keyframe, exact }`, где
  `exact: true` означает «поток начнёт ровно с этой секунды». Эта же секунда уходит в
  шкалу, субтитры и сохранённую позицию, поэтому «1:59:41» на экране — это то же, что в
  файле, и позиция продолжения не «прыгает»;
- **сервер больше не переспрашивает ffprobe на перемотке** (ключевой кадр нужен только
  копированию, а его на перемотке нет): перемотка стала быстрее, а `movies.remux_start`
  пишет `requested`, `from`, `aligned` и `exact` — видно, что поток шёл точным seek;
- **индекс ключевых кадров и `KEYFRAME_EPS`** остались для режима копирования
  (`/torrent/seek?copy=1`) — он по-прежнему доступен по API, но плеер им не пользуется;
- **таймкоды после реза восстанавливаются**: `-fflags +genpts`,
  `-avoid_negative_ts make_zero` и `-af aresample=async=1:first_pts=0` (звук прибит к
  нулю вместо накопленного дрейфа от AAC-priming и сдвига дорожек MKV), а при
  копировании ещё и `-fps_mode passthrough`.

**Кадр вписывается по размеру окна.** Плеер сам считает размер блока (`fitVideoBox`):
кадр занимает всю доступную ширину, а если места по высоте меньше — всю высоту, так что
фильм виден целиком, без обрезки и без чёрных полей по бокам. В полном экране — на весь
экран.

**Управление загрузкой.** Раздачу можно **остановить** («Стоп»: канал освобождается, скачанное
остаётся на диске), **возобновить** (по сохранённому `.torrent`-метафайлу из
`storage/torrents/meta` или по magnet) и **удалить** вместе со скачанными файлами.
Всё это есть и в окне плеера, и во вкладке **«Скачанные»** — она находится в панели страницы сразу
справа от **«Статистики»** и показывает реестр загрузок (что качается, что остановлено, что уже
скачано) с живым прогрессом, скоростью, пирами и ссылкой «Смотреть дальше».

**Галочка «хранить скачанный торрент после просмотра»** (в плеере и в шапке вкладки «Скачанные»)
хранится в `settings.json` (`movies.keepTorrentFiles`, по умолчанию **включена**):

- включена — раздача остаётся в списке, файлы на диске, докачка продолжается в фоне;
- выключена — завершённая раздача удаляется вместе с файлами (кнопка «Убрать лишнее» делает то же
  для всех досмотренных), а незавершённая просто останавливается: окно, закрытое случайно, можно
  вернуть и продолжить.

**Случайно закрытое окно возвращается.** Каждая раздача попадает в реестр загрузок
(`server/ts/torrent.ts` → `torrent_downloads` в `storage/data.json`) вместе с названием фильма,
поэтому при повторном клике по фильму плеер открывает **ту же самую загрузку**, а не пустое окно, и
продолжает с сохранённой секунды (позиция пишется не чаще раза в 5 секунд и при закрытии).

**FFmpeg (выбор дорожек и переупаковка на лету).** Плеер показывает строку состояния: путь и версию,
если FFmpeg найден, либо куда положить бинарь, если нет (`storage\ffmpeg`) — рядом есть кнопка
«Проверить снова», которая заново сканирует диск, не дожидаясь кэша определения (12 секунд).
Поиск бинаря рекурсивный (до 3 уровней вглубь), поэтому архив, распакованный «как скачалось»
(`storage\ffmpeg\ffmpeg-<версия>-essentials_build\bin\ffmpeg.exe`), тоже находится. Если дорожки не
прочитались, приложение больше не говорит «FFmpeg не установлен» на любой сбой: причину видно прямо
(`ffprobe` не найден / не удалось прочитать контейнер), а для потока торрента делается повторная
попытка — сразу после добавления раздачи данных в стриме может ещё не быть.

**Фильтры выдачи.** В выдаче площадки смешаны 4K/1080p/720p, живые и почти мёртвые раздачи. Над
списком есть два фильтра: **«Разрешение»** (только значения, которые реально есть в этой выдаче) и
**«Сиды»** (порог «от 5/10/20/50/100»). Сиды — это те, кто раздаёт файл, и именно их число определяет
скорость скачивания; личеры её не добавляют, поэтому фильтр считается по сидам. Рядом — счётчик
«Показано N из M» по обоим фильтрам сразу.

### Обновления приложения

Обновления **обязательны** (с версии 0.2.2): так у всех пользователей одна и та же сборка, а не смесь старых версий с несовместимыми настройками.

- проверка запускается **при каждом старте** приложения (и каждые 4 часа, пока оно открыто); выключателя в интерфейсе нет — в `settings.json` ключ `general.autoUpdate` остался для совместимости и приводится к `true` разовой миграцией;
- новая версия **скачивается автоматически** в фоне, без вопросов;
- когда установщик скачан, появляется диалог с единственной кнопкой **«Перезапустить и установить»**: закрыть его без обновления нельзя — кнопка, «крестик» и Esc ведут к одному и тому же, приложение перезапускается и ставит новую версию;
- если скачать не удалось (нет сети, CDN недоступен), приложение **продолжает работать**, а проверка повторяется по таймеру и при следующем запуске: блокировать пользователя из-за недоступной сети нельзя;
- установщик заменяет только файлы программы — папка `storage` (настройки, БД, записи лекций, загрузки) не затрагивается.

В Настройках остались ручные **«Проверить обновления»** и **«Скачать и установить»** — если не хочется ждать фоновой проверки.

### Экспорт и импорт настроек

В **Настройках** есть раздел **«Настройки: экспорт и импорт»** — переносит конфигурацию между компьютерами одним JSON-файлом `moonapp-settings-<дата>.json`:

- **все секции `settings.json`** — то есть настройки всех страниц (чат, лекции, видео, музыка, сжатие, обход блокировок, Web Archive, внешний вид, производительность и т.д.);
- **локальные настройки интерфейса** (то, что живёт не в `settings.json`, а в браузерном хранилище — например, конфиг ИИ-чата, прогресс панели задач);
- **ключи API** — только если включить переключатель «Включить ключи API и токены» (по умолчанию выключен; файл с ключами нельзя передавать третьим лицам).

При импорте применяются только известные приложению поля: неизвестные и несовместимые по типу значения пропускаются, и приложение сообщает, сколько их было. Файл можно править руками, но безопаснее импортировать его целиком.

**Чего в файле нет:** заметок, задач, истории чатов, подписок и узлов прокси, списка «Фильмы» — это данные, а не настройки; для них есть резервные копии (раздел «Автобэкап»). Часть системных настроек (автозапуск, размер окна, аппаратное ускорение) применяется после перезапуска приложения — об этом приложение сообщает после импорта.

### Логи и диагностика

Если что-то работает не так — в **Настройках** есть раздел **«Логи и диагностика»** с кнопкой **«Собрать логи»**. Она собирает один текстовый файл со всеми событиями приложения:

- нажатия и переходы между страницами (что и во сколько открыли);
- изменения полей и горячие клавиши;
- изменения настроек с указанием страницы (`settings.change`: страница, путь, значение);
- **настройки по каждой странице** (магазин, конвертер, сжатие видео, видео/музыка, книги, монитор, ИИ-чат, синтез речи, лекции, обход блокировок, web-архив, заметки) — эффективные значения, а также локальные настройки интерфейса, которые хранятся не в `settings.json`;
- все запросы к локальному API, установки и скачивания;
- предупреждения и ошибки (интерфейса и сервера), включая ошибки Electron.

Файл `MoonApp-logs-<дата>-<время>.txt` появляется в папке `storage\` рядом с программой — его можно сразу переслать разработчику (кнопки «Показать в проводнике» и «Копировать путь»). Значения секретов и API-ключей в отчёт не попадают: для них пишутся только имена полей. Хранятся последние 10 отчётов.

## Безопасность

- Локальный API слушает только `127.0.0.1`, каждый запрос требует сессионный токен (передаётся файлом, не через argv).
- Жёсткий CSP в Electron-окне: инлайн-скрипты и внешние загрузки запрещены.
- HTML из скачанных веб-архивов отдаётся с вырезанными скриптами (`script-src 'none'`).
- Секреты шифруются через Electron safeStorage (DPAPI) с фолбэком на AES-256-GCM.
